# Решения команды

Короткий журнал решений, которые держат работу с репозиторием и проектом.
Новое решение дописывается снизу: дата, что решили, почему, что из этого следует.

## Р-01 · 25.09 · Слияние только merge-коммитом

**Решение.** PR сливаются только merge-коммитом. Squash и rebase в настройках репозитория
выключаются (Settings → General → Pull Requests: оставить только «Allow merge commits»).

**Почему.** В `main` и `dev` должны попадать личные коммиты со своими авторами: по ним
преподаватель видит вклад каждого, а GitHub строит график вклада. Squash склеивает коммиты
в один от имени того, кто нажал кнопку.

**Следствие.** Кнопку «Squash and merge» не нажимаем, даже если она доступна.
Настройку в репозитории переключает администратор (Никита).

## Р-02 · 25.09 · Защита `main` и ветка `dev`

**Решение.**
- Работа идёт в ветках задач: одна задача — одна ветка — один PR. Имя ветки указано в issue
  (`nikita/NG-00-repo-setup`, `vlad/VP-04-exercise-director`, ...).
- PR из ветки задачи идёт в `dev`. В конце спринта `dev` сливается в `main` одним PR,
  и `main` всегда содержит состояние, которое показывали на вехе.
- Защита `main` (правило ветки): запрет прямого push и force-push, запрет удаления,
  слияние только через PR. Обязательное одобрение не включаем: в команде четыре человека,
  и при болезни одного ревьюера PR встанет. Ревью по `CODEOWNERS` держится на договорённости:
  свой PR никто не сливает без отзыва второго владельца пути.
- Для `dev` защиты нет, но правила те же: только через PR, только merge-коммит.

**Почему.** Без защиты правила держатся на договорённости (ТЗ §9.1); минимальная защита
снимает самые дорогие ошибки (force-push и прямой коммит в `main`) и не блокирует работу.

**Следствие.** Правило ветки для `main` включает администратор (Никита) в
Settings → Branches. До этого правило выполняется по договорённости.

## Р-03 · 25.09 · Главную сцену правит один человек

**Решение.** `Assets/_Rubezh/Scenes/Main.unity` правит только Никита. Остальные работают в
своих песочницах `Assets/_Rubezh/Scenes/Sandbox/Sandbox_<Имя>.unity` и отдают префабы.

**Почему.** Конфликт слияния в сцене Unity разбирается плохо даже через UnityYAMLMerge
(`NG-02`); проще его не допускать.

## Р-04 · 09.10 · Исходники `.blend` в `Art/Source~`

**Решение.** Файлы `.blend` лежат в `Assets/_Rubezh/Art/Source~/`, в Unity попадают только FBX.

**Почему.** Unity импортирует `.blend` сам, запуская установленный Blender. У кого Blender не
установлен или стоит не по стандартному пути (Steam), в консоли ошибка «Blender could not be
found», а правило «проект открывается без ошибок в консоли» нарушено. Папку с `~` на конце Unity
не видит, а git и Git LFS хранят её как обычно.

**Следствие.** Пути `Art/Source/*.blend` в Issues читаем как `Art/Source~/*.blend`.
Настройки экспорта — `docs/art-pipeline.md`.

## Р-05 · 23.10 · Управление пистолетом в руке

**Решение.** Кнопки читаются только с руки на `Grip_Primary`: A/X — отделить магазин, B/Y —
предохранитель (переключение), нажатие стика — снять затвор с задержки, Trigger — спуск
(выстрел при нажатии от 0,75, отпускание ниже 0,4 — `RulesConfig`). Затвор — Grip второй рукой на
`Slide`, потянуть назад и отпустить. Рука, которая держит пистолет первой, — основная; если она
отпустила, основной становится вторая. При двух руках поворот — среднее двух рук
(`TwoHandedAverage`).

**Почему.** Стик руки с пистолетом всё равно выключен (локомоция — другой рукой), а большой
палец на стике там же, где на настоящем пистолете рычаг затворной задержки. Отдельный
коллайдер для рычага `SlideStop` в 3 мм от `Slide` рука в шлеме различает плохо. Гистерезис
спуска не даёт очереди от дрожания пальца на пороге. `TwoHandedAverage` выбран без шлема:
у поддерживающей руки под рукоятью направление «первая → вторая» почти вертикально, и режим
`FirstHandDirectedTowardsSecondHand` задирал бы ствол; подтвердить в шлеме (`NG-19`).

**Следствие.** Подсказка `onb_pistol_buttons` (`docs/hints.md`) дополняется «стик: затвор с
задержки» при правке сценария (`YG-14`).

## Р-06 · 25.09 · Сборка под Quest — платформа Android с настройками профиля Meta Quest

**Решение.** Активная платформа проекта — Android. Настройки, которые задаёт профиль сборки
Meta Quest, выставлены в Player Settings явно: Vulkan, min API 29, target API 32, IL2CPP,
ARM64, Stereo Rendering Path — Instancing; XR Plug-in Management → Android → OpenXR, группа
Meta Quest Support (`MetaQuestFeature`, список устройств quest…quest3s), профиль контроллеров
Oculus Touch, Automatic Dynamic Resolution. Пакет Unity OpenXR: Meta не ставим.

**Почему.** Отдельный ассет профиля Meta Quest в Build Profiles создаётся, только если Unity Hub
отметил платформу как установленную. У части команды Unity 6000.3.24f1 стоит без Hub (нет прав
администратора), и такой профиль не создаётся, а настройки платформы Android с теми же значениями
дают тот же APK: манифест с `com.oculus.intent.category.VR`, `android.hardware.vr.headtracking` и
`com.oculus.supportedDevices`. Значения не зависят от того, у кого какой Hub.

**Следствие.** Для сборки Android SDK Platform 32 обязателен (target API). Без Hub его ставит
`sdkmanager "platforms;android-32"` из `AndroidPlayer/SDK/cmdline-tools`. Проверка APK:
`aapt dump badging Builds/Rubezh.apk` — sdkVersion 29, targetSdkVersion 32.

## Р-07 · 04.12 · Исключение к ТЗ §7.3 п. 4: оттенок очков постпроцессингом

**Решение.** Постпроцессинг на Quest разрешён в одном месте: Color Adjustments → Color Filter, пока
надеты очки (`NG-30`). Рисует его только On Tile Post Processing (Untethered XR); встроенный
постпроцессинг рендерера выключен, других эффектов нет. Выключатель —
`RulesConfig.glassesTintEnabled`.

**Почему.** Дизайн-документ §7, объект 5: в очках «слегка меняется цветопередача» — это
подтверждение, что очки надеты, без лишнего текста. On-tile цветокоррекция не создаёт
промежуточных текстур (документация Unity 6.3, «On-tile post-processing»), поэтому укладывается в
ограничения Quest 2 из §7.3.

**Следствие.** Замер до и после — `docs/qa/perf.md`. Если на шлеме меньше 72 Гц при стрельбе,
галка снимается и исключение отменяется. Строка 28 протокола `NG-19` проверяет оттенок в шлеме.


## Р-08 · 06.11 · Ствол вне сектора — только штраф, без стопа

**Решение.** `MuzzleOutOfSector` всегда мелкое нарушение: −10 и замечание у контроллера, когда ствол
вернулся в сектор, при любой длительности заноса и заряженности оружия. Упражнение по сектору не
останавливается. Грубым остаётся выстрел вне сектора (`ShotOutOfSector`, FR-36).

**Почему.** На прогоне в шлеме упражнение обрывалось на «Заряжай»: магазин с патронами делает оружие
заряженным, и любой занос ствола дольше 1,5 с во время вставки магазина и досылания давал стоп.
Новичок, для которого тренажёр сделан, почти каждый раз не доходил до стрельбы.

**Следствие.** `SectorRule` не знает о заряженности. `sectorGraceSeconds` теперь значит только порог
прощения заноса вне рубежа (#164). Строка 2 протокола `NG-19` проверяет долгий занос без стопа.

## Р-09 · 06.11 · Грубое нарушение не останавливает упражнение

**Решение.** `LookIntoMuzzle`, `ShotBeforeFire`, `ShotAfterCease`, `ShotOutOfSector` остаются грубыми, но
упражнение не прерывают: у контроллера красное замечание, упражнение идёт до сдачи в шкаф, итог — 0 баллов
и «не зачёт», причина — первое грубое нарушение (`ExerciseResult.FailReason`). Фазы `Failed` в обычном
прохождении нет, стоп-экран не показывается, экран результата — сразу у R1.

**Почему.** На прогоне в шлеме новичок почти каждый раз не доходил до стрельбы и разряжания: остановка
отнимала у него именно ту часть упражнения, ради которой тренажёр. Оценка не мягче: грубое — всё так же
«не зачёт».

**Следствие.** `MuzzleLookRule` пишет одно нарушение на эпизод взгляда (раньше лишние гасил стоп).
`InstructorVoice` не говорит «Стоп! Упражнение прекращено». Протокол `NG-19`, строки 5, 10–12, 33.

## Р-10 · 06.11 · Предметы — только рукой; плавный ход левым стиком

**Решение.** Луч Near-Far Interactor больше не берёт 3D-предметы: в маске его кастера
(`Left_NearFarInteractor.prefab`, правая рука — вариант) только слой UI, кнопки экранов нажимаются лучом
как раньше. Предмет берётся ближним захватом — рукой вплотную. Левый стик — плавный ход
(`DynamicMoveProvider`, 2,5 м/с, `Left Controller → Smooth Motion`), правый — телепорт и поворот.

**Почему.** Захват лучом с расстояния ломал ощущение «взял оружие в руки» и обходил закон Фиттса из
`user-flow.md` §2; перемещение только телепортом в шлеме показалось неудобным.

**Следствие.** `AnchorLocator` и так берёт ближайший якорь, поэтому шаги и подсказки работают и при ходьбе.
Ногами можно зайти за линию огня — барьера нет. Онбординг: «Левый стик: идти · правый стик вперёд: телепорт».
